## P7 예약 점검 (2026-10-19)

- 목적: 정기적으로 관리하는 사이트를 주기마다 자동 점검한다. 운영 가이드 부록2의 "게시판 1일 1회 이상 점검"을 자동화하는 기능이다. done/06에서 '확장 계획'(R17)으로 미뤄 둔 항목이다
- 방식: 상주 프로세스 없이 **Windows 작업 스케줄러**에 맡긴다. 창을 닫아도, 재부팅해도 예약이 남는다
  - 저장 → `schtasks /create /tn adGuard\<id> /tr "adguard.exe --scheduled <id>" /sc DAILY|WEEKLY|MONTHLY /mo <간격> /st HH:MM [/d 요일|날짜] /f`
  - 주기: 매일, 매주(요일 여러 개), 매월(1~28일) × 1~12일·주·개월마다. 29~31일은 짧은 달에 건너뛰어서 받지 않는다
  - 목록 원본은 `schedules.json`(주소·주기·시간 상한). 작업 스케줄러에는 id만 넘겨 `/tr` 길이 제한(261자)과 주소 인용 문제를 피한다. 사이트(호스트) 하나에 예약 하나라서, 같은 사이트로 다시 저장하면 같은 id의 작업을 덮어쓴다(수정)
  - 화면 (10/19 시안 3개 중 B 선택): 따로 목록을 두지 않고 **사이트 현황 한 줄에 통합**한다
    - 예약한 사이트 줄에 예약 칩 "⏱ 주기 · 다음 실행"(`schtasks /query /fo csv /nh` 표기 그대로). 작업 스케줄러에 없으면 빨간 칩
    - 줄의 "예약"과 사이트 현황 머리의 **"+ 예약 추가"**는 같은 예약 창(10/19 창 시안 3개 중 A: 칸 이름 + 반복·간격·요일/날짜·시각·시간 상한, 왼쪽 아래 "예약 삭제". 설명 문구는 넣지 않음). "+ 예약 추가"에만 주소 칸. 첫 점검 없이도 예약할 수 있다. 예약만 있는 사이트는 "아직 점검 안 함" 줄로 맨 앞에 나오고 버튼은 "지금 점검"
    - 버린 시안: A(사이트 현황과 따로 예약 목록, 같은 사이트가 두 번 나오고 수정 불가), C(예약 관리 탭 + 주간 달력, 첫 화면이 복잡해지고 구현량이 많음)
  - 삭제: 작업 스케줄러에서 지우지 못해도 목록에서는 뺀다. 남은 작업이 돌더라도 목록에 없는 id라 바로 끝난다
- 결과: `--scheduled`는 `run_all`(보고서 포함)을 그대로 쓴다. `records/`에 쌓여 사이트 현황·지난 점검 대비에 바로 나온다. 콘솔은 숨기고 진행 기록은 `logs/날짜.log`에 남긴다
- 동시 실행: `logs/scan.lock` 잠금(Windows `msvcrt.locking`, 그 밖은 `flock`). 프로세스가 죽으면 OS가 풀어 준다
  - 예약 점검: 잠겨 있으면 30초마다 다시 시도한다(최대 60분)
  - 창 모드: 잠겨 있으면 "예약 점검이 진행 중입니다"를 띄운다
  - 명령줄 모드(채점용)는 잠그지 않는다. 적격평가 동작은 바뀌지 않는다
- 한계(사용설명서 5장): schtasks 기본 설정이라 PC가 꺼져 있었거나 로그인하지 않은 회차는 건너뛰고, 배터리 전원으로는 시작하지 않는다. 필요하면 `/xml`로 StartWhenAvailable·DisallowStartIfOnBatteries=false를 넣는다. 결과 알림(토스트)은 없다. 사이트 현황에서 확인한다
- 확인 (macOS, schtasks만 가짜로 바꿈)
  - 예비 서버 화면: "+ 예약 추가"로 처음 보는 사이트 매월 15일 → "아직 점검 안 함" 줄 생김, 기존 사이트 줄에서 매주 월·금 → 칩 표시, 같은 사이트를 매일로 다시 저장 → 같은 id로 `/create /f`(수정), 끄기 → `/delete`와 줄 사라짐, 빈 주소는 "점검할 주소를 입력하세요", 작업 스케줄러에 없는 예약은 빨간 칩
  - `main.py --scheduled <id>`로 S1 실제 점검 → 30.8초, records·logs 기록, S1 채점 100점. 없는 id는 바로 끝남
  - 잠금: 다른 프로세스가 잡고 있으면 `take_lock()`이 None이고, 창 모드 start는 안내 문구를 돌려주고 idle 유지. 풀린 뒤에는 다시 잡힘
