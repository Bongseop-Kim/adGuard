# 결과 화면·보고서 UX와 LLM 비용·호출 방식 보완 조사

- 작성: 2026-10-14 (모든 출처는 이 날짜에 열어서 확인함)
- 범위: 06 문서 §3(R1~R19)와 07 문서(Decisions API 설계: 규칙→AI cascade, 해시 캐시, 마스킹, 거부 폴백, 호출 수·토큰 표시)에 **없는 것만** 다룬다. 이미 있는 내용은 "유지"라고만 적었다.
- 본심사 기준: 실무 활용성 20점(이해 쉬움, 원인·근거 충실, 안내·관리 기능), 도입 가능성 10점(안정 구동, 운영 쉬움, 비용 적정, **AI 토큰 사용량·호출 방식**)
- 난이도 표기: 하 = 반나절 이하, 중 = 1일 안팎, 상 = 2일 이상 (9일 일정 기준)

## 핵심 결론 (우선순위순)

1. **"AI 사용 명세서"를 보고서 부록과 화면 패널로 만든다.** 심사위원이 보는 것은 단가가 아니라 "몇 건 중 몇 건만, 왜, 얼마에, AI가 실제로 무엇을 바꿨는지"다. 퍼널(후보 → 규칙 확정 → AI 전송 → 캐시 적중 → AI가 바꾼 판정) + 실측 토큰·원화 비용 + AI 끄고 돌린 결과와의 차이를 한 표로 보여준다. FrugalGPT·산업 cascade 논문이 성과를 "비용 대비 정확도"로 보고하는 방식과 같다. (§2-1)
2. **오탐률 목표와 "오탐 신고" 버튼을 제품 지표로 둔다.** Google Tricorder는 코드 리뷰 경고의 실효 오탐 10% 미만을 기준으로 삼고, "Not useful" 클릭 비율이 10%를 넘으면 분석기를 끈다. R18(오탐 처리)을 "이번 점검 오탐 표시율"로 집계해 보고서에 싣는다. (§1-1)
3. **기본 목록은 "같은 원인 1건 + 영향 페이지 N개"로 묶는다.** GitHub code scanning은 관련 경로를 알림 하나로 묶고, 지문(`partialFingerprints`)으로 실행 간 같은 알림을 식별한다. 우리 R11(이력 비교)과 R14(템플릿 삽입 묶음)를 **안정적인 지문 ID** 하나로 같이 해결한다. (§1-2)
4. **설명은 "구조화된 근거"로, 문장 생성은 하지 않는다.** 실제 모더레이터 실험(ACL 2024)에서 일반적인 설명은 무시되고 구조화된 설명만 판단 시간을 7.4% 줄였다. 카카오는 LLM으로 분류 결과를 문장으로 다시 써서 운영자를 돕는다. 우리는 Decisions API가 글을 만들지 않으므로 **규칙 신호로 템플릿 문장을 만든다(토큰 0)**. (§1-3)
5. **R6 "숨김 드러내기" 캡처는 `locator.screenshot`이 아니라 `page.screenshot(clip=…, style=…)`로 만든다.** Playwright의 `locator.screenshot`은 요소가 보일 때까지 기다리므로 숨김 요소에서는 시간 초과가 날 수 있다. `style` 옵션(캡처 순간에만 CSS 적용)과 `mask` 옵션(개인정보 가리기)을 쓰면 원본 페이지를 건드리지 않고 전/후 두 장을 얻는다. (§1-4)
6. **AI 캐시를 실행 간에도 유지한다(디스크 캐시).** 07의 캐시는 한 번의 점검 안에서만 쓰인다. 일일 점검(부록2 "1일 1회")에서는 같은 푸터·배너가 매일 나오므로, 지난번 답을 다시 쓰면 2회차부터 AI 호출이 거의 0이 된다. 캐시 키에 모델명과 질문 버전을 넣는다. (§2-2)
7. **단일 HTML 보고서는 "JSON 1개 내장 + 바닐라 JS 렌더러" 구조로 만든다.** Lighthouse가 이 구조를 쓰고, `</script>` 탈출을 막으려고 `<`를 이스케이프한다. 화면(pywebview)과 보고서가 같은 렌더러를 쓰면 9일 안에 둘 다 만들 수 있다. Excel은 **UTF-8 BOM CSV**가 Microsoft 공식 안내상 더블클릭으로 바로 열린다. 의존성 0으로 R9를 채운다. (§1-5)
8. **Batch API 할인은 쓸 수 없다고 명시한다.** OpenAI Batch API(50% 할인, 24시간 창) 지원 목록에 `/v1/decisions`가 없다. 심사위원이 "배치 할인은 왜 안 썼나"를 물으면 답할 수 있게 사용설명서·기획서에 적어 둔다. 대신 우리가 줄이는 것은 비용보다 **외부 전송량과 지연**이라는 쪽으로 설명한다. (§2-3)

## 1. 결과 화면·보고서 UX

### 1-1. 경고 피로(alert fatigue)와 오탐 관리: 지표로 만든다

| 항목 | 내용 |
|---|---|
| 발견 | ① Google은 코드 리뷰에 노출하는 검사의 기준으로 "이해하기 쉬울 것, 조치 가능하고 고치는 법을 안내할 것, **실효 오탐 10% 미만**(개발자가 90% 이상 실제 문제라고 느낄 것)"을 둔다. "실효 오탐"은 **사람이 보고도 조치하지 않은 경고**로 정의한다(기술적으로 맞아도 조치 안 하면 오탐). ② Tricorder는 결과마다 "Please fix"·"Not useful" 버튼을 둔다. "Not useful"을 누르면 분석기 담당 팀에 버그가 자동 등록되고, **"Not useful" 비율이 10%를 넘으면 그 분석기를 끈다.** ③ 개발자가 정적 분석을 안 쓰는 이유로 "조치할 수 없는 경고", "오탐 때문에 신뢰하지 않음", "워크플로에 통합 안 됨"을 든다. ④ Johnson 외(ICSE 2013, 개발자 20명 인터뷰): 도구가 유익하다고 느끼면서도 **오탐과 경고를 보여주는 방식**이 사용을 막는 장벽이었다. ⑤ (참고, 벤더 설문) FireEye/IDC 2021: 분석가가 받는 알림 중 45%가 오탐이라고 응답, 35%는 알림을 무시한다고 응답 — **원문 리포트는 열지 못했고 검색 요약으로만 확인** |
| 출처 | CACM 2018-04 "Lessons from Building Static Analysis Tools at Google" https://cacm.acm.org/research/lessons-from-building-static-analysis-tools-at-google/ (브라우저로 본문 확인) · Johnson et al. ICSE 2013 https://research.google/pubs/pub43477/ (초록 확인) · FireEye 설문은 https://www.securitysales.com/business/industry/fireeye-soc-report-alert-fatigue/ (검색 결과로만 확인, 미열람) |
| 시사점 | **추가:** ① R8 조치 상태의 '오탐'을 집계해 보고서 요약에 "이번 점검 오탐 표시 N건(M%)"을 싣는다. 우리 쪽 목표도 "오탐 10% 미만"으로 기획서에 적는다(Google 기준 인용 가능). ② 오탐 표시 시 **사유 선택(접근성 숨김 / 정상 공지 / 회사명·단위 / 기타)**을 받는다. 이 사유가 R18 예외 규칙과 다음 버전 규칙 개선 근거가 된다(Tricorder의 "Not useful → 버그" 고리와 같은 구조). ③ "검토 필요"(07 §6.4, q 0.25~0.4) 항목은 **기본 목록에서 분리된 탭**에 두어 확정 위반 목록의 정밀도를 지킨다 |
| 난이도 | 하 (집계·드롭다운) |

### 1-2. 묶음 표시와 안정적인 지문 ID (R11·R14·R15를 한 번에)

| 항목 | 내용 |
|---|---|
| 발견 | ① GitHub code scanning은 실행마다 결과를 맞추기 위해 **지문(fingerprint)**을 쓴다. SARIF의 `partialFingerprints`로 "두 결과가 논리적으로 같은지" 판단하고, 지문이 없으면 "중복 알림이 보일 수 있다". 파일 경로가 실행마다 달라지면 매번 새 알림이 생긴다. ② 데이터 흐름 경고는 **관련 경로를 알림 하나로 묶고** 경로를 펼쳐 보게 한다. ③ 알림에는 **처음 생긴 시점**이 표시된다. ④ 해제(dismiss) 시 사유를 고르고 선택적으로 코멘트를 남기며, 이 코멘트는 **타임라인에 기록되어 "감사·보고 시 근거"로 쓸 수 있다**. 해제된 같은 코드는 다음 실행에서 다시 알리지 않고, 필요하면 다시 열 수 있다 |
| 출처 | https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/sarif-support-for-code-scanning · https://docs.github.com/en/code-security/code-scanning/managing-code-scanning-alerts/about-code-scanning-alerts · https://docs.github.com/en/code-security/code-scanning/managing-code-scanning-alerts/resolving-code-scanning-alerts |
| 시사점 | **추가(설계 결정):** 검출마다 `fingerprint = hash(정규화된 광고 텍스트 + 기법 + location에서 변하는 부분을 뺀 경로)`를 만든다. 쿼리스트링의 세션값·게시글 번호 정렬 순서 등은 빼야 한다. 이 하나로 ① R11 신규/지속/해결/재발 판정 ② R18 오탐 예외 ③ R14 "같은 지문이 여러 URL에 → 템플릿 삽입 의심"이 동시에 된다. **화면:** 목록 기본 보기는 "지문 단위 1행 + 영향 URL N개(펼치기)", `result.json`은 규칙대로 위치별로 낸다. 각 행에 **최초 발견일**(이력 DB 기준)을 표시. 오탐 처리 이력(누가·언제·사유)은 보고서에 남겨 감사 증빙으로 쓴다 |
| 난이도 | 중 (지문 정의가 핵심, 저장은 JSON 파일로 충분) |

### 1-3. 근거 설명: "구조화된 근거"가 실제로 빠르다

| 항목 | 내용 |
|---|---|
| 발견 | ① Calabrese 외(ACL 2024, **실제 모더레이터 대상** 실험): "일반적인 설명은 판단 속도에 영향이 없고 자주 무시된다", "**구조화된 설명은 판단 시간을 7.4% 줄인다**". (초록만 확인. '구조화'의 구체 형태는 본문 미확인) ② 카카오 스팸 대응 조직(2024-07-05 게시, 제6회 Kakao Tech Meet): LLM을 분류에 쓰고, "**분류 결과를 문장으로 재생성함으로써 스팸을 모니터링하는 운영자들에게 실질적인 도움**"을 준다고 발표. (게시물은 인터뷰만 있음. 파이프라인·비용 수치는 영상 안에 있을 것으로 보이나 **미확인**) ③ Semgrep은 AI가 오탐을 판정하면 PR 코멘트를 보내지 않고 별도 화면에 모아, 보안팀이 동의하면 닫고 동의하지 않으면 다시 연다. 관리자는 AI 제안의 최소 confidence를 설정한다. "오탐 분류 정확도 95% 이상"이라고 자체 주장 |
| 출처 | https://arxiv.org/abs/2406.04106 · https://tech.kakao.com/posts/626 (브라우저로 확인) · https://docs.semgrep.dev/semgrep-assistant/overview (현재 "Semgrep Multimodal" 문서로 바뀜) |
| 시사점 | **변경:** R5 근거 상세 맨 위에 **한 줄 판정 요약**을 고정 형식으로 둔다. 예: `[숨김] 화면 밖 배치(left:-9999px) · [광고] 텔레그램 ID 1, 첫충 키워드 · [AI] 광고일 확률 92%(도박)`. 문장은 규칙 신호로 템플릿 생성 → 토큰 0, 재현 가능. 생성형 LLM으로 설명문을 쓰지 않는다(07의 "판단 전용 API" 결정과 맞음). **추가:** AI가 '광고 아님'으로 본 경계 후보는 Semgrep처럼 "AI 제외 N건" 묶음으로 따로 보여주고 담당자가 **동의/이의**를 누르게 한다 → 이의는 '위반'으로 복구 |
| 난이도 | 하 |

### 1-4. 증거 시각화: 숨김 드러내기 캡처를 만드는 방법

| 항목 | 내용 |
|---|---|
| 발견 | ① Playwright `locator.screenshot()`은 "actionability 검사를 기다린 뒤 요소를 화면에 스크롤해서" 찍는다 → 숨김 요소에서는 대기·실패 가능. 캡처는 요소 크기로 잘리고 위를 덮은 요소도 찍힌다. ② `style` 옵션: "캡처하는 동안에만 적용할 스타일시트 텍스트", Shadow DOM과 하위 프레임에도 적용. ③ `mask` 옵션: 지정 요소를 색 박스로 덮음(기본 `#FF00FF`), 보이지 않는 요소에도 적용. ④ `animations:"disabled"`로 애니메이션을 멈춰 캡처를 안정화. ⑤ WAVE는 결과 아이콘을 **페이지 위 해당 위치에 직접 삽입**하고, 색(빨강=오류, 노랑=검토 필요, 초록=기능)으로 구분한다. **스타일을 끄면 CSS로 숨겨진 항목의 아이콘도 보이게** 한다. 단 아이콘 삽입이 레이아웃을 깨뜨린다고 스스로 밝힌다. ⑥ BackstopJS 보고서는 기준·테스트·차이 이미지 비교와 슬라이더("scrubber")를 제공(작동 방식 세부는 문서에 없음) |
| 출처 | https://playwright.dev/docs/api/class-locator (locator.screenshot, locator.highlight) · https://wave.webaim.org/help · https://github.com/garris/BackstopJS |
| 시사점 | **구현 방식 결정(R6):** "이용자에게 보이는 화면" = 숨김 요소를 감싼 **부모 영역** 좌표로 `page.screenshot(clip=부모 bbox)`. "드러낸 화면" = 같은 clip에 `style="[data-adg='ID']{position:static!important;left:auto!important;opacity:1!important;color:#000!important;font-size:14px!important;clip:auto!important;outline:3px solid red!important}"`. 화면 밖(-9999px) 요소는 부모 영역 안으로 끌어오므로 같은 clip에서 비교된다. 탐지 중에 DOM에 `data-adg` 속성만 붙여 두면 된다. **추가:** 게시판 캡처에 작성자명·연락처 칸이 찍히면 `mask`로 가린다(보고서가 공문 첨부·외부 신고에 쓰이므로). **선택:** WAVE식 "페이지 위 표시"는 레이아웃 문제와 공수 때문에 **빼도 됨**. 대신 전체 페이지 축소 캡처에 빨간 박스로 위치만 표시(화면 밖 요소는 가장자리 화살표) |
| 난이도 | 중 (요소 유형별 style 조합 테스트 필요. 캡처는 검출 시간 측정 뒤 별도 단계로 돌려 점수에 영향 없게) |

### 1-5. 단일 HTML 보고서 패턴 (9일 안에)

| 항목 | 내용 |
|---|---|
| 발견 | ① Lighthouse 보고서 생성기는 "필요한 모든 것을 HTML 문자열 하나로 합친다". 렌더러는 **전부 클라이언트 JS**이고 **`innerHTML`을 일부러 쓰지 않고** `createElement`와 `<template>`을 쓴다. ## 2. LLM 비용·호출 방식

07 문서에 이미 있음(유지): 규칙→AI cascade, 확실 양성·음성은 AI 미전송, 실행 내 해시 캐시, 동시 4개·5초 타임아웃·60초 예산, 거부·실패 시 규칙 폴백, 마스킹, 호출 수·토큰·비용·거부 수 화면 표시, 실제 전송 텍스트 공개.

### 2-1. 심사위원에게 "토큰 사용량·호출 방식"을 보여주는 법

| 항목 | 내용 |
|---|---|
| 발견 | ① FrugalGPT(Chen·Zaharia·Zou, 2023): 비용 절감 전략을 **프롬프트 축소, 근사(완료 캐시 등), cascade** 셋으로 정리. cascade는 싼 단계의 답을 신뢰도 점수 g(q,a)로 평가해 임계값을 넘으면 멈추고 아니면 다음 단계로 보낸다. 성과를 "GPT-4와 같은 성능에 **최대 98% 비용 절감**, 같은 비용에 정확도 4% 향상"처럼 **비용-정확도 쌍**으로 보고한다. ② Filter-And-Refine(산업 영상 모더레이션, 2025): 가벼운 라우터 + MLLM cascade로 전량 MLLM 대비 **계산 비용 1.5%**, 기존 분류기 대비 F1 66.50% 향상, 자동 처리량 41% 증가. ③ LLM Performance Predictors(AAMAS 2026): 로그확률·엔트로피 등으로 "LLM 판정을 믿을지, 사람에게 넘길지"를 정하는 비용 고려 선택적 분류. "고위험은 넘기고 나머지는 자동화" |
| 출처 | https://arxiv.org/abs/2305.05176 , https://arxiv.org/html/2305.05176 · https://arxiv.org/abs/2507.17204 · https://arxiv.org/abs/2601.07006 |
| 시사점 | **추가 — "AI 사용 명세서"(보고서 부록 + 화면 패널, 기획서 표에도 그대로):** <br>① **퍼널:** 후보 N → 규칙 확정 양성 a / 확정 음성 b → AI 전송 c(전체의 x%) → 캐시 적중 d → 실제 API 호출 e → 거부 f·실패 g(규칙 폴백) <br>② **AI가 바꾼 판정:** 규칙만이면 출력됐을 것을 AI가 뺀 건수, 반대로 AI가 넣은 건수, "검토 필요"로 보낸 건수 — **AI의 가치가 숫자로 보이는 유일한 칸** <br>③ **실측 사용량:** `usage.input_tokens` 합계, 호출당 평균·최대 토큰, 비용(USD·원화, 환율 가정 표기), 추가 지연(p50·p95), 응답 `model` 값 <br>④ **연간 환산:** "1일 1회 점검 × 365일 × 실측 비용" (2회차부터 디스크 캐시 효과 반영, §2-2) <br>⑤ **AI 끔 대비 비교(실험값):** eval 시나리오에서 규칙만 vs 규칙+AI의 정밀도·재현율과 비용 — FrugalGPT식 비용-정확도 쌍. 07 §8 실험 결과를 그대로 넣는다 <br>⑥ **호출 방식 그림:** 07 §6.1 파이프라인 그림에 각 화살표의 건수를 적은 판(산키형 막대 하나면 충분) <br>기획서 문구: "AI는 전체 후보의 x%에만, 건당 약 550토큰, 점검 1회 약 ○원. 출력 토큰 0, 결과는 확률로 받아 임계값으로 라우팅" |
| 난이도 | 하~중 (카운터는 07 설계에 이미 있음. ②·⑤가 새 작업) |

### 2-3. Batch API·질의 묶기: 쓰지 않는 이유를 명시

| 항목 | 내용 |
|---|---|
| 발견 | ① OpenAI Batch API는 동기 API 대비 **50% 할인**, 완료 창은 **24시간만** 가능. 지원 엔드포인트는 `/v1/responses`, `/v1/chat/completions`, `/v1/embeddings`, `/v1/completions`, `/v1/moderations`, 이미지 2종이며 **`/v1/decisions`는 없음.** ② Decisions 가이드는 "독립적인 질문은 같은 `questions` 배열에 넣어 공유 입력을 평가하라"고만 하고, **여러 입력을 한 요청에 묶는 방법은 문서에 없다.** 질문·지시문이 입력 토큰에 어떻게 계산되는지도 설명이 없다. 임계값은 "애플리케이션의 레이블 예시로 정하고, 오탐·미탐 비용에 따라 고르라"고 권고. 거부 처리 권고는 예제 코드에서 `refusal` 타입을 확인하는 것뿐 ③ FrugalGPT의 "질의 연결(query concatenation)"은 여러 질의를 한 프롬프트에 넣어 프롬프트 반복 비용을 줄인다 |
| 출처 | https://developers.openai.com/api/docs/guides/batch · https://developers.openai.com/api/docs/guides/decisions · https://arxiv.org/html/2305.05176 |
| 시사점 | **기획서·사용설명서에 추가:** "Batch API(50% 할인)는 Decisions API를 지원하지 않고 24시간 비동기라 실시간 점검에 맞지 않는다." **빼도 됨:** 여러 후보를 한 입력에 묶는 질의 연결은 하지 않는다. 07 §6.6 추정상 요청당 550토큰 중 질문이 약 350토큰이라 묶으면 토큰은 줄지만, 비용이 이미 점검 1회 수 센트 수준이고 Jev 문서의 "관계없는 내용이 많으면 정확도 하락" 약점과 충돌한다. 대신 **질문 지시문 길이**를 줄이는 쪽(FrugalGPT의 프롬프트 축소)을 §8 실험 변형에 넣는다: 현재 지시문 vs 축약판의 정확도·토큰 비교 |
| 난이도 | 하 (문서 작업) |

### 2-4. 거부(refusal)·무료 대안

| 항목 | 내용 |
|---|---|
| 발견 | ① OpenAI Moderation 엔드포인트(`omni-moderation-latest`)는 **무료**이고 텍스트·이미지를 받는다. 범주는 harassment, hate, illicit(불법 행위 방법 안내), self-harm, sexual, violence 등이며 **도박 범주는 없다.** 언어 지원 언급 없음. ② 거부 예측 연구(Reuter·Schulze 2023)는 프롬프트만 보고 ChatGPT 거부 여부를 76% 정확도로 예측. 거부 분류 체계 연구(2412.16974)는 16개 거부 범주를 제시 — 둘 다 검색 결과 요약으로만 확인, 원문 미열람 |
| 출처 | https://developers.openai.com/api/docs/guides/moderation · (미열람) https://arxiv.org/pdf/2306.03423 , https://arxiv.org/abs/2412.16974v1 |
| 시사점 | **유지:** 07의 "거부 = 규칙 폴백"이 맞다. **빼도 됨:** Moderation API를 거부 대비 2차 판정으로 쓰는 안은 도박 범주가 없어 우리 핵심 유형(도박)에 쓸모가 없다. 성인(sexual)·마약(illicit)만 부분 보완 가능하지만 공수 대비 가치 낮음. **추가(작음):** 거부율을 AI 사용 명세서에 **범주별**(ad_category 규칙 추정값 기준)로 표기 → "성인 문구에서 거부가 몰린다" 같은 사실을 정직하게 보여주면 도입 가능성 평가에서 신뢰를 얻는다 |
| 난이도 | 하 |
