## 1. 정상 숨김과 악성 숨김 구분 (P3, P5)

### 근거
- **Google 스팸 정책** (developers.google.com/search/docs/essentials/spam-policies, "Hidden text and link abuse"): 흰 글자·화면 밖 배치·글자 크기 0 등을 숨김 텍스트 남용으로 정의하면서, 다음은 **위반이 아니라고 명시**한다
  - 아코디언·탭처럼 펼치고 접는 콘텐츠
  - 여러 이미지·문단을 순환하는 슬라이드
  - 사용자가 상호작용하면 보이는 툴팁
  - "화면낭독기 전용으로, 화면낭독기 사용자 경험을 높이려는 텍스트"
- **숨긴 링크 연구** (arXiv 1303.2438, 중국 홈페이지 576만 개 조사): 숨김 기법 12종 분류. 실제 비중은 JS로 숨김 39.9%, 화면 밖 24.5%, display/visibility 10.8%로 셋이 75%. 드롭다운 메뉴 같은 정상 용도와 남용을 가르는 기준은 없어서 오탐이 "상당히 많았다"고 적는다. → **CSS만으로는 정상/악성을 못 가른다는 것이 선행 연구의 한계**
- **KRDS 숨긴 콘텐츠 컴포넌트** (krds.go.kr component_11_02): 공공 사이트 표준이 시각적으로 숨긴 텍스트를 쓰도록 안내한다. 실제 CSS는 `.sr-only`, `.blind`: `position:absolute; width:1px; height:1px; margin:-1px; overflow:hidden; clip:rect(0,0,0,0); white-space:nowrap`. 용도는 "복잡한 대체 설명, 조작 안내, 상태 변화 안내"
- **그누보드 실제 CSS** (사이트 A에서 확인): `#hd_h1 { position:absolute; font-size:0; line-height:0; overflow:hidden }`, `.sound_only { position:absolute; top:0; left:0; width:0; height:0; font-size:0; … overflow:hidden }`. `#hd_h1`에는 페이지 제목(=글 제목)이 들어간다
- **사이트 D 확인**: 숨은 `textarea.textarea`는 댓글마다 있는 "수정" 입력창이고, 같은 원문이 화면에 `p.commt_txt`로 보인다

### 해결 방향
1. **"화면에 같은 글이 보이는가"를 먼저 본다** (가장 강한 신호). 숨긴 요소의 글이 같은 페이지의 보이는 요소에 그대로(공백 정리 후) 있으면, 그 숨김은 광고를 감추려는 것이 아니다. P3의 `#hd_h1`(본문 `span.bo_v_tit`에 같은 제목), P5의 수정 폼(`p.commt_txt`에 같은 원문)을 모두 이 규칙 하나로 거른다
   - 보이는 쪽이 4종 변형(HOMOGLYPH·JAMO)이면 그것은 그대로 보이는 변형으로 보고한다 (A의 `span.bo_v_tit`)
2. **정상 숨김 지문**: 다음 패턴은 "숨김 광고" 대신 "사이트가 숨긴 영역"으로 분류하고, 1번 조건이 맞으면 보고하지 않는다
   - 화면낭독기 전용: 클래스 `sr-only`·`sr_only`·`blind`·`sound_only`·`visually-hidden`·`hidden`·`IR`·`hide`, 또는 CSS 지문 `clip:rect(0,0,0,0)`/`clip-path:inset(50%)` + 1px 이하 크기
   - 폼 값: `textarea`, `input`의 값 (렌더링된 글이 아니라 입력값)
   - 닫힌 UI: `details:not([open])`, `[role=tabpanel][hidden]`, `aria-expanded="false"`가 가리키는 영역(`aria-controls`)
3. **조심할 점**: 스패머도 `sr-only`를 쓸 수 있다. 그래서 2번만으로 빼지 말고 **1번(보이는 곳에 같은 글)과 함께** 쓸 때만 제외한다. 화면 어디에도 없는 광고가 sr-only에 있으면 그대로 OFFSCREEN으로 보고한다. 사이트 F(댓글 영역 전체를 `left:-99999px`로 숨김)는 보이는 곳에 같은 글이 없으므로 계속 검출된다
4. 채점 영향: 출제 사이트가 "접근성용 숨김 + 정상 문구"를 함정으로 넣을 가능성이 높다 (research/02). 1~3은 그 함정에도 맞는다

## 2. 해킹 삽입과 게시물 스팸 구분 (P2)

### 근거
- **Google "Hacked content"** 정의: 코드 삽입(JS·iframe), 페이지 삽입(새 스팸 페이지), 콘텐츠 삽입("검색엔진은 보지만 사용자는 찾기 어렵게 숨긴 링크·텍스트"), 리다이렉트. 즉 해킹 삽입은 **사이트 운영자의 템플릿·소스 쪽**에 들어간다
- **템플릿 탐지** (Bar-Yossef & Rajagopalan, WWW 2002): 페이지를 "pagelet"(링크 k=3개 이상인 자식이 없는 가장 큰 요소)으로 나누고, 같은 지문(shingle)이 여러 페이지에 반복되면 템플릿으로 본다. 평균 43%의 페이지가 템플릿 pagelet을 포함. → **"여러 페이지에 반복"은 템플릿이라는 뜻이지 해킹이라는 뜻이 아니다.** 해킹 판정에는 반복 + "그 반복이 원래 템플릿에 없던 것"이 필요하다
- **SEISE** (Liao et al., IEEE S&P 2016): .gov·.edu·.mil에서 홍보 감염 11,000곳(전체의 약 3%)을 오탐 1.5%로 찾았다. 핵심은 "사이트의 원래 주제와 삽입된 홍보 문구의 **의미적 불일치**". 기존의 리다이렉트 추적·시간 변화 관찰은 확장이 어렵다고 지적
- **인도네시아 .go.id 연구** (Nurseno 2023): 감염 사이트에서 투명화·hidden 속성·배경색 일치로 도박 링크를 숨긴 사례와, 같은 IP를 공유하는 감염 하위 도메인 망을 보고. 숨김 + 사이트 전반 반복이 해킹의 전형
- **사이트 A 확인**: 반복이 생긴 곳은 (1) `#hd_h1`(글 제목이 들어가는 공통 머리), (2) 이전/다음 글 링크 `li.btn_prv > a`(href가 같은 게시판의 다른 글)

### 해결 방향
현재 규칙 "같은 지문이 2개 이상 페이지의 같은 위치"에 다음 예외를 둔다.
1. **글 제목 반영**: 반복된 문구가 그 페이지 본문 제목(또는 보이는 요소)과 같으면 게시물형. (`#hd_h1`)
2. **이웃 글 링크**: 반복 요소가 같은 사이트의 글 상세 주소를 가리키는 `<a>`이고 문구가 그 대상 글의 제목이면, 그 대상 글 1곳의 게시물형 검출로 합친다. (`btn_prv`·`btn_next`, 목록, "최근 글" 위젯)
3. **사용자 작성 영역**: 위치가 게시판 본문·댓글 영역 안이면(그누보드 `#bo_v_con`·`.cmt_contents`, XE `.xe_content`, 전자정부 `.view_cont`·`.reply` 등, 또는 작성자·작성일 요소의 형제) 게시물형
4. 위 셋에 해당하지 않으면서 **템플릿 영역(머리·꼬리·메뉴 등 거의 모든 페이지에 있는 pagelet)에 숨겨진 광고**만 해킹 의심으로 둔다. 숨김 여부를 함께 보면 .go.id 연구의 전형과 맞는다
5. (확장) SEISE처럼 "사이트 주제와의 불일치"를 점수로 보조 설명에 넣을 수 있다. 공공 사이트는 주제가 분명해서 효과가 크지만 이번 범위에서는 규칙 1~4로 충분하다

## 3. 유사 문자·전각·보이지 않는 문자 (P4, P6)

### 근거
- **UTS #39 Unicode Security Mechanisms**: 혼동 판정 `skeleton(X)` = NFD → **Default_Ignorable_Code_Point 제거** → confusables 대표 문자로 치환 → NFD. 혼합 문자 판정에서 한글+한자는 `Kore`로 단일 문자 체계, 라틴+한글+한자는 "Highly Restrictive"로 허용 범위. 즉 **한글 단어 안에 라틴 한 글자(`ㅋr`)가 섞이는 것은 혼합 문자**로 판정된다
- **Unicode DerivedCoreProperties.txt** (최신판에서 확인): Default_Ignorable_Code_Point에 `00AD`(소프트 하이픈), `200B..200F`(폭 없는 공백·결합자·방향 표시), `2060..206F`, `FEFF`, `FE00..FE0F`(이체자 선택자)와 함께 **한글 채움 문자 `115F`, `1160`, `3164`(ㅤ), `FFA0`**이 들어 있다. 한국어 스팸이 "빈칸처럼 보이는 문자"로 쓰는 것들이다
- **Bad Characters** (Boucher et al., IEEE S&P 2022): 보이지 않는 문자(ZWSP·ZWNJ·ZWJ), 유사 문자, 방향 재배치(Bidi), 삭제 문자 4종 공격. 방어는 "표준 보이지 않는 문자 집합을 입력에서 제거하면 막힌다", 유사 문자는 "가장 막기 어렵다", 렌더링 후 OCR 비교는 보이지 않는 문자·재배치·삭제를 100% 막음
- **한국어 변형 연구**: PHISH (Kim et al., arXiv 2505.21380)는 한글의 음운 특성을 이용한 치환으로, 자모 하나만 바꿔도 혐오 표현 탐지기 F1이 최대 11.8점 떨어진다. 고성민 외(2024, ScienceON JAKO202414157600169)는 의도적으로 변형한 비속어를 개체명 인식(시퀀스 레이블링)으로 찾는다. → 사전 기반 정규화의 빈틈을 학습으로 메우는 방향이지만, 이번 도구는 규칙 + AI 판정(todo/08) 구조라 규칙 쪽 정규화를 먼저 넓힌다
- **사이트 D 확인 결과** (`textcheck.check()` 직접 실행)
  - `온라인바카라 † く 【￥ bcc777。COM ￥】 ぅ`: NFKC로 `￥→¥`는 바뀌지만 `。`(U+3002)은 마침표로 안 바뀌고, 가나 섞기는 판정 대상이 아님 → HOMOGLYPH 없음
  - `카­지노`(U+00AD 삽입): 키워드는 찾지만 `ad: False`, 기법 없음

### 해결 방향
1. **정규화 순서 고정**: 원문 → Default_Ignorable 제거(위 목록 전체, 한글 채움 문자 포함) → NFKC → 문장 부호 유사 문자(`。`→`.`, `｡`→`.`, `ㆍ`은 유지) → confusables. 광고성 판정은 이 결과로 한다. 소프트 하이픈 사례는 이것만으로 광고로 잡힌다
2. **기법 귀속**: 
   - 보이지 않는 문자가 키워드 글자 **사이에** 끼어 있으면 → 4종에는 없으므로 **추가 탐지 유형 "보이지 않는 문자 삽입"**으로 보고 (todo/08, 본심사 창의성 항목). result.json에는 넣지 않는다
   - 전각 영숫자(`ＣＯＭ`)·`。`로 주소·키워드를 바꾼 경우 → HOMOGLYPH (모집요강 정의에 "전각 문자"가 명시)
   - 광고 키워드 사이에 의미 없는 가나·기호를 끼운 경우 → 기법 4종에는 없으므로 추가 유형 "잡음 문자 삽입" 후보
3. **P4 기법 하나로 정하기**: UTS #39 기준으로 `ㅋr`은 "한글 자모 + 라틴 혼합"이다. 판정 원칙을 "라틴·숫자·키릴 등 **다른 문자 체계가 끼어 있으면 HOMOGLYPH**, 한글 자모만으로 쪼갰으면 JAMO"로 정하면 한 요소에서 둘이 겹치지 않는다. 다만 모집요강의 JAMO 예시 `ㅋㅏㅈㅣㄴㅗ`, HOMOGLYPH 예시(키릴·전각·숫자)와 맞춰 보면 이 원칙이 맞는다. 둘 다 걸리는 경우를 정답이 둘 다 요구할지는 알 수 없으므로 **결정 기록(decisions)으로 남기고**, 테스트 사이트(eval)에 같은 표기를 넣어 점수 영향을 확인한다

## 4. 같은 페이지의 다른 주소 (P7, P8, P12)

### 근거
- **DUST** (Bar-Yossef, Keidar, Schonfeld, WWW 2007 / TWEB 2009): 서버가 별칭·리다이렉트·파라미터로 같은 페이지를 여러 주소로 만든다. DustBuster는 **페이지 내용을 보지 않고 URL 목록만으로** "치환 규칙"과 "무관한 파라미터 제거 규칙"을 찾고, 몇 개만 실제로 받아 검증한다. 상위 10개 규칙의 최대 90%가 유효, **크롤량 최대 26% 감소**
- **Koppula et al.** (WSDM 2010): 내용 지문이 같은 URL 묶음에서 정규화 규칙(무관한 파라미터 제거 등)을 배워 일반화. 정밀도 95% 이상에서 DUST 규칙(22%)보다 큰 **60% 중복 감소**
- **Google canonical**: `rel=canonical`은 "대표 주소" 힌트이며, 같은 canonical을 가진 주소는 같은 페이지로 묶는다
- **사이트 E 확인**: 정렬·보기 꼬리표가 다른 주소가 같은 canonical(`board_vqqG39/1381`)을 가리키는데, 목록 부분이 달라 내용 해시가 달랐다

### 해결 방향
1. **canonical 우선 중복 제거**: 방문 결과의 canonical(같은 호스트일 때)이 이미 방문한 결과의 canonical과 같으면 새 결과로 세지 않는다. 지금은 canonical을 "출력 URL"로만 쓰고 중복 판정에는 쓰지 않는다
2. **본문 해시**: 내용 해시를 페이지 전체가 아니라 템플릿(여러 페이지 공통 pagelet)과 목록 영역을 뺀 본문으로 계산한다 (Bar-Yossef 2002와 같은 발상). 1번으로 대부분 해결되므로 2순위
3. **알려진 꼬리표 추가** (즉시): XE·Rhymix `sort_index`, `order_type`, `listStyle`, `category`(목록일 때), `search_target`, `search_keyword`, `page`(글 ID가 있을 때) / 회원 화면 `act=dispMember*`는 탐색 제외
4. **자동 학습** (확장): 같은 경로에서 파라미터 하나만 다른 두 주소의 본문 해시가 같으면 그 파라미터를 "무관"으로 표시하고, 이후 큐에 넣을 때 제거한다 (Koppula 방식의 온라인 축소판). 사이트마다 꼬리표 이름을 미리 알 필요가 없어진다
5. **P12**: 쿼리 값에 이미지·문서 확장자가 들어 있는 주소(`view_image.php?fn=…jpg`)는 페이지가 아니므로 큐에서 제외

## 5. 크롤러 안전성과 부담 조절 (P1, P10, P11, P9)

### 근거
- **RFC 9110 §9.2.1**: GET은 "안전한(safe)" 메서드로 서버 상태를 바꾸지 않아야 한다. 위험 주소 차단은 이 원칙을 어기는 사이트를 위한 방어이고, **사용자가 직접 넣은 시작 주소는 명시적 의도**라서 막을 이유가 없다
- **사이트 E 확인**: 언어 선택이 `<a href="#" onclick="doChangeLangType('zh-TW')">`로 되어 있어 클릭 탐색 대상이 된다. 누르면 세션 언어 쿠키가 바뀌어 이후 페이지가 다른 언어로 나온다
- **Scrapy AutoThrottle** (docs.scrapy.org): 도메인별로 "응답 지연 / 목표 동시성"을 목표 지연으로 잡고 이전 지연과 평균. **200이 아닌 응답의 지연은 지연을 줄이는 데 쓰지 않는다.** 시작 5초, 최대 60초
- **Chrome DevTools Protocol** `Page.captureScreenshot`: `format`으로 `jpeg`·`png`·`webp`를 지원한다 (Playwright `page.screenshot`은 jpeg·png만)

### 해결 방향
1. **P1**: 시작 주소(와 그 리다이렉트 최종 주소)는 DANGER·DOWNLOAD 필터를 건너뛴다. 필터에 걸린 다른 주소 수를 진행 기록에 남기고, 시작 주소가 HTML이 아닌 경우는 "열지 못함"과 다른 안내를 낸다
2. **P10**: 클릭 탐색 제외 목록에 언어 전환(함수 이름에 `lang`, `doChangeLangType`, `hreflang` 속성, `lang=` 파라미터로 가는 링크)을 넣는다. 빈 검색 버튼(검색 입력이 비어 있는 폼의 submit)도 누르지 않는다. 혹시 바뀌어도 되돌리도록, 컨텍스트 생성 때 `locale="ko-KR"`·`Accept-Language`를 고정하는 것은 이미 되어 있다
3. **P11**: 실패할 때 원인(타임아웃·연결 실패·HTTP 상태)을 한 줄씩 진행 기록에 남긴다. 그다음에 AutoThrottle처럼 "지연이 늘면 천천히, 줄면 다시 빠르게"로 바꿀지 판단한다. 지금의 "연속 3번 실패 → 절반"은 실패 원인을 구분하지 못한다
4. **P9**: 캡처를 CDP로 WebP 저장하면 같은 품질에서 JPEG보다 작다(측정 필요). 같은 원인 유형의 묶음이 많으면 대표 N개만 캡처하고, `records/` 사본에는 캡처를 빼고 결과 데이터만 둔다(필요하면 다시 찍기)

## 구현 순서 제안

1. P1 시작 주소 예외 (작음, 오작동이 큼)
2. P3·P5 "보이는 곳에 같은 글이면 숨김 제외" + 정상 숨김 지문 (eval에 접근성 숨김·수정 폼 함정 추가)
3. P2 해킹 판정 예외 3종
4. P6 정규화(Default_Ignorable·NFKC·`。`) + P4 기법 귀속 원칙 (decisions 기록 + eval 추가)
5. P7·P8·P10·P12 크롤 낭비 줄이기
6. P9·P11 운영 편의

각 단계마다 S0~S5 점수·시간이 그대로인지, 사이트 A·D·E에서 문제 수치가 줄었는지 확인한다.
