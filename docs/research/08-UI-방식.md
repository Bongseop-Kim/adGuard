# UI 방식 비교: 실행 파일 안에서 화면을 띄우는 방법

- 작성: 2026-10-14
- 질문: 제출물이 실행 파일인데 로컬 HTTP 서버 + 브라우저 창 방식이 맞는가? 더 나은 방법이 있는가?
- 담당 평가 항목: 본심사 실무 활용성 20점(화면), 도입 가능성 10점(안정 구동), 실행 실패로 인한 0점 방지
- 방법: browser-use로 Microsoft WebView2 문서, pywebview 공식 문서·이슈, 비교 자료 열람

## 결론

**pywebview(Windows에서는 WebView2 사용)로 바꾸는 것을 추천한다.** 서버·포트·Edge 의존 없이 실행 파일이 자기 창을 띄우고, 화면은 HTML로 그대로 만든다. 단, pywebview 창이 실패하면 지금 방식(로컬 서버 + 기본 브라우저)으로 넘어가는 예비 경로를 둔다.

## 비교

| 방식 | 서버·포트 | 창 | Windows 11 기본 구성만으로 실행 | 화면 표현력 | 패키징 위험 |
|---|---|---|---|---|---|
| **pywebview (WebView2)** | **없음.** JS↔Python 직접 호출 | **자기 창** (exe 이름·아이콘) | **예.** WebView2 런타임이 Windows 11 OS 구성요소로 기본 설치됨 | HTML·CSS·JS 그대로 | 중간: pythonnet(.NET) DLL 추가, PyInstaller 공식 지원 |
| 로컬 HTTP 서버 + Edge `--app` (현재 안) | 127.0.0.1 임의 포트 | Edge 창 (주소창 없음) | 예 (Edge 기본 설치) | HTML 그대로 | 낮음: 표준 라이브러리만 |
| tkinter | 없음 | 자기 창 | 예 (Python에 포함) | 낮음: 표·하이라이트·필터 구현이 어렵고 투박함 | 낮음 |
| NiceGUI native 모드 | 있음 (내부 FastAPI 서버 + pywebview 창) | 자기 창 | 예 | 높음 | 높음: 의존성 많음 |
| Eel | 있음 (로컬 서버 + 웹소켓) | Chrome/Edge 앱 창 | 예 | HTML | 현재 안과 같은 구조라 이점 없음 |
| Flet | 있음 (Flutter 클라이언트와 로컬 소켓 통신) | 자기 창 | 예 | 높음, 단 HTML이 아니라 Flet 위젯 | 높음: 용량 증가, 새 프레임워크 학습 |
| PySide6 (Qt WebEngine) | 없음 | 자기 창 | 예 | HTML | 높음: Chromium을 하나 더 넣어 수백 MB |

## 근거

| 사실 | 출처 |
|---|---|
| "Evergreen WebView2 Runtime은 Windows 11 운영체제의 일부로 모든 Windows 11 기기에 미리 설치되어 있다" | Microsoft Learn, *Evergreen vs. fixed version of the WebView2 Runtime* (browser-use로 직접 확인) |
| 다만 앱은 만들기 전에 런타임이 있는지 확인하는 것이 좋다 (레지스트리 또는 API) | Microsoft Learn, *Distribute your app and the WebView2 Runtime* |
| pywebview는 HTTP 서버 없이 JS↔Python 양방향 통신 제공 (`js_api`, `evaluate_js`, 6.0부터 `window.state` 공유 상태) | pywebview 문서 *Javascript–Python bridge* |
| Windows 의존성은 pythonnet(.NET 4 이상) + WebView2 런타임 | pywebview 문서 *Installation* |
| PyInstaller 공식 지원. HTML은 `--add-data`로 넣는다. 설치된 다른 GUI 백엔드(PyQt 등)까지 끌어오므로 `excludes` 필요 | pywebview 문서 *Freezing* |
| PyInstaller로 묶은 뒤 HTML 경로를 못 찾아 404가 나는 사례가 있음 → 경로 처리 주의 | pywebview 이슈 #1402 |
| pywebview는 메인 스레드에서 실행해야 한다 | pywebview 이슈 #1251 |
| 최신 버전 6.2.1 | PyPI (2026-10-14 확인) |

## 우리 앱에 적용할 때

- **스레드 구성:** 메인 스레드는 pywebview 창을 띄우고, 탐지는 작업 스레드에서 돌린다. Playwright sync API는 그 작업 스레드 안에서 만든다. 진행 상황은 `window.state` 또는 `evaluate_js`로 화면에 보낸다.
- **시간 측정:** "탐지 시작" 버튼은 `js_api`로 Python 함수를 직접 부른다. 측정 시작점이 서버 왕복 없이 클릭 시점과 같아진다.
- **명령줄 모드는 유지한다:** `adguard.exe <URL>`을 실행하면 창 없이 탐지해서 `result.json`을 쓴다 (지금 골격).
- **예비 경로:** WebView2 창 생성이 실패하면(런타임 없음, 정책 차단) 로컬 서버 + 기본 브라우저로 같은 HTML을 연다. 화면 코드를 하나로 쓰려면, 화면이 Python을 부르는 부분을 얇은 어댑터(pywebview `js_api` 또는 `fetch`)로 감싼다.
- **용량:** pythonnet과 pywebview가 추가된다. 브라우저 동봉분(약 170MB)에 비하면 작을 것으로 예상하지만, CI에서 실측한다.
- **검증:** 도입 전에 CI(Windows)에서 pywebview 창 + 작업 스레드의 Playwright 조합으로 빌드·실행을 확인한다.

## 결정 전에 확인할 것

1. CI에서 pywebview + Playwright exe가 빌드·실행되는가 (러너에 화면이 없으므로 창 생성 직후 종료하는 스모크 모드로)
2. 늘어나는 용량
3. 실제 Windows 11 PC에서 창이 정상으로 뜨는가 (todo/07에서 함께 확인)

## 검증 결과 (2026-10-14, GitHub Actions windows-latest)

- pywebview 6.2.1 + Playwright 1.64.0을 PyInstaller onedir로 빌드 성공 (추가 설정 없음)
- `adguard.exe --smoke-gui <URL>`: WebView2 창이 뜨고 → JS에서 `pywebview.api.start()` 호출 → 작업 스레드에서 동봉 Chromium으로 탐지 → 진행 메시지를 창에 표시 → `result.json` 생성 → 창 종료까지 통과. 경로는 한글·공백 경로(`C:\테스트 폴더\adguard\`)
- 명령줄 모드(`adguard.exe <URL>`)도 같은 빌드에서 통과
- 용량 증가: webview 1.2MB + pythonnet 0.6MB + clr_loader ≈ **2MB**. 브라우저를 뺀 빌드는 128.3MB이고 그중 playwright(드라이버)가 102.4MB. artifact(압축) 170MB → 172MB
- **결정: UI는 pywebview(WebView2)로 한다.** 로컬 서버 + 기본 브라우저는 WebView2 실패 시 예비 경로로만 둔다 (todo/06)
- 남은 확인: 실제 Windows 11 PC에서 창 표시 (todo/07). 현재 빌드는 콘솔 창이 함께 뜬다. 창 모드에서 콘솔을 숨길지(`--windowed` + 로그 파일)는 todo/06에서 정한다
