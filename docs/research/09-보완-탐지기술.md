## 1. 크기 0 + `overflow:auto` 상자 — 04 규칙이 놓친다 (직접 확인)

**발견**
- Kaspersky Securelist가 실제 SEO 스팸 주입 사례 4개를 공개했다. 그중 예시 2는 `overflow: auto; position: absolute; height: 0pt; width: 0pt;` 상자 안에 링크를 넣었다. 예시 3은 `height:0; overflow:hidden; color:transparent`, 예시 4는 `position:absolute; left:-9232px`다. 예시 1·2의 링크에는 `rel="dofollow"`가 붙어 있었다(이 문서의 집계: 블록당 링크 15~23개).
- 04 §2.1 5)는 "overflow auto/scroll이면 scrollWidth/Height까지 영역을 넓힘(스크롤하면 보임)"이다. 직접 확인한 결과, 위 상자는 `clientWidth/Height = 0×0`, `scrollWidth/Height = 16×114`였다. 그래서 04 규칙대로면 스크롤 영역으로 넓혀져 **"보임"으로 판정되어 놓친다.** `checkVisibility()`도 true였다.

**시사점 (변경)**: 스크롤 확장보다 먼저 "조상 박스의 client 영역이 2px 미만이면 잘림"을 검사한다. 스크롤 확장은 client 영역이 사람이 스크롤할 수 있는 크기(가로·세로 모두 ≥ 2px, 권장 ≥ 10px)일 때만 적용한다. 테스트 사이트에 이 케이스를 그대로 추가한다.

**난이도**: 매우 낮음 (조건문 1개).

**출처**: Securelist, Anna Larkina, "SEO spam and hidden links: how to protect your website and your reputation", 2025-10-17 — https://securelist.com/seo-spam-hidden-links/117782/

## 2. 줄 수 제한(line-clamp) 미리보기 오탐 (직접 확인)

**발견**: 04 §2.1 5)는 "visible = 보이는 면적 합 / 전체 면적 합 < 0.05면 잘림"이다. 게시판 목록에서 흔한 `display:-webkit-box; -webkit-line-clamp:2; overflow:hidden` 미리보기에 긴 본문(81줄)을 넣었더니 visible이 **0.037**로 나왔다. 그래서 OFFSCREEN으로 판정된다. 스팸 글의 미리보기는 광고성 점수도 통과하므로 그대로 오탐이 된다. 이 글은 실제로는 보이는 광고다(4종 기법이 아니다).

**시사점 (변경)**: 면적 합 비율 대신 **"한 줄이라도 충분히 보이면 보임"** 으로 바꾼다. 텍스트 rect 중 하나라도 `rect ∩ clipBox`의 높이가 rect 높이의 35% 이상이고 너비가 1글자 이상이면 보이는 텍스트로 본다. 또는 `-webkit-line-clamp`·`text-overflow`가 있는 요소는 첫 rect만 본다. 04 케이스 46(말줄임)과 함께 회귀 테스트에 넣는다.

**난이도**: 매우 낮음.

## 3. 스크린샷 차분 방식 수정 (직접 확인)

**발견**
1. **04 §3.1 규칙 3("글자 채움색 alpha < 0.1이면 TRANSPARENT")은 그라데이션 글자를 잘못 잡는다.** 제목 꾸밈으로 흔한 `background-image:linear-gradient(…); background-clip:text; color:transparent; -webkit-text-fill-color:transparent`는 글자가 **보이는데도** fill이 투명이다.
2. **04 §3.3 차분 방식(글자를 color/text-fill transparent로 바꾸고 다시 찍기)도 같은 경우를 "안 보임"으로 확정한다.** 이 글자는 원래 fill이 투명이고 배경이 그려지므로, 바꾸기 전과 후의 이미지가 같다. 직접 확인: 차이 없음 → 오판.
3. **대신 텍스트 노드를 `<span>`으로 감싸고 그 span에만 `visibility:hidden`을 거는 방식을 쓰면 4개 경우가 모두 맞았다.**

   | 케이스 | 차이 > 24인 픽셀 | 판정 |
   |---|---|---|
   | 그라데이션 글자(background-clip:text) | 2,908 | 보임 (정답) |
   | `color:transparent` | 0 | 안 보임 (정답) |
   | `#eee` 배경 상자 위 `#eee` 글자 | 0 (최대 차이 1) | 안 보임 (정답) |
   | `#eee` 위 `#333` 글자 | 2,467 | 보임 (정답) |
   | 흰 그라데이션 위 흰 글자 | 0 | 안 보임 (정답) |

   - 요소 전체에 `visibility:hidden`을 걸면 안 된다. 그 요소의 배경 상자까지 사라져서 "보임"으로 오판한다.
4. **PNG 바이트를 비교하면 안 된다.** `#eee` 위 `#eee`는 안티앨리어싱 때문에 최대 차이 1이 생겨서 바이트가 달랐다. 04의 임계값 방식(차이 > 24, 글자 면적의 1%)을 반드시 쓴다.
5. **`locator.screenshot()`은 숨김 요소에서 30초 동안 기다린다.** Playwright는 요소가 "visible"이 될 때까지 기다린다. visibility:hidden, display:none, 크기 0인 후보에 쓰면 후보마다 30초 타임아웃이 걸린다(직접 확인: TimeoutError). **`page.screenshot(clip=rect, animations="disabled", caret="hide")`** 를 쓴다.

**시사점 (변경)**
- 규칙 3에 예외를 둔다. 요소에 `background-clip: text`(또는 `-webkit-background-clip: text`)가 있고 `background-image`가 none이 아니면 **불확정 → 차분**으로 보낸다.
- §3.3 차분은 "텍스트 노드를 span으로 감싸고 그 span에 visibility:hidden" 방식으로 바꾼다. 이 방식은 mix-blend-mode에도 그대로 쓸 수 있다.
- 스크린샷은 page 단위 clip으로만 찍는다.

**난이도**: 낮음 (반나절).

## 4. marquee 은닉 (직접 확인 + 논문)

**발견**
- DMoS(USENIX Security 2021)는 중국 상용 사이트 7,000여 곳의 웹 페이지 3,800만 개 이상을 분석했다. 주입에 쓰인 태그는 44종이었고, 그중 **`marquee`, `a`, `title`, `meta`가 67%** 였다. 논문은 "marquee 태그는 scrollamount와 scrolldelay 속성으로 내용을 시각적으로 숨기기 편해서 널리 쓰인다"고 설명한다. 또한 변조된 페이지의 26%는 주입된 태그가 1개뿐이었고, 70%는 10개 미만이었다(최소 주입).
- 04 §2.3은 marquee에 대해 "500ms 뒤 다시 측정해서 위치가 바뀌면 숨김이 아니다"라고 정했다. 직접 확인 결과(300ms 간격으로 10번 표본 측정, 값 = marquee 상자 안에 들어온 글자 면적 비율):

  | 케이스 | 측정값 | 04 규칙의 판정 |
  |---|---|---|
  | 기본 marquee(정상 공지) | 0.01 → 1.0 | 보임 (정답) |
  | `scrollamount="99999"` | 10번 모두 0 | 위치는 계속 바뀌므로 **"보임"으로 오판** |
  | `scrolldelay="9999999" truespeed` | 10번 모두 0 | 위치가 고정이므로 숨김 (정답) |
  | `width=1 height=1` | 10번 모두 0 | 숨김 (정답) |

**시사점 (변경)**: marquee 안의 텍스트는 2~3초 동안 300ms 간격으로 표본을 찍는다. **모든 표본에서 보이는 비율이 0.05 미만이면 OFFSCREEN**으로 본다. 위치가 바뀌는지는 보지 않는다. 보조 규칙으로 `scrollamount`가 상자 폭보다 크거나(사실상 순간 이동) `scrolldelay`가 10초 이상이면 숨김 신호로 둔다. 기법 코드는 위치 계열이므로 OFFSCREEN이다. marquee 미끼(정상 흐르는 공지)도 테스트 사이트에 둔다.

**난이도**: 낮음. 다만 표본 측정에 페이지당 2~3초가 걸리므로 **marquee가 있는 페이지에서만** 측정한다.

**출처**: Yang et al., "Scalable Detection of Promotional Website Defacements in Black Hat SEO Campaigns", USENIX Security 2021 — https://www.usenix.org/conference/usenixsecurity21/presentation/yang-ronghai (PDF 본문 §5에서 직접 확인)

## 5. "보이는 글자열" 재구성 (직접 확인 + 논문)

DOM의 글자 순서와 화면에 보이는 글자 순서가 다르면 키워드 매칭이 실패한다. 직접 확인한 결과는 다음과 같다(`textContent` / `innerText` / 화면 표시).

| 케이스 | textContent | innerText | 화면 |
|---|---|---|---|
| `카<span style=font-size:0>xq</span>지<span style=display:none>zz</span>노` (salting) | 카xq지zz노 | **카xq지노** | 카지노 |
| `direction:rtl; unicode-bidi:bidi-override`로 `노지카` | 노지카 | 노지카 | 카지노 |
| flex `order:3/1/2`로 `노`,`카`,`지` | 노카지 | 노\n카\n지 | 카지노 |
| `::before{content:"토토사이트 가입코드"}` | 없음 | 없음 | 보임 |

- **salting**: Cisco Talos(2025-10-07)는 1년 넘게 관측한 결과를 이렇게 정리했다. ① 키워드 사이에 무작위 고정 길이 문자열을 넣는다. ② 브랜드명 글자 사이에 ZWSP·ZWNJ를 넣는다. ③ `bdo` 같은 선택자 하나에 font-size:0을 걸어 문서 전체의 키워드를 쪼갠다. ④ "큰 텍스트를 반지름 0인 원 안에 넣는다". 04는 숨긴 조각 자체를 후보로 보지만, **숨긴 조각을 뺀 부모 쪽 문장**은 매칭하지 않는다. `innerText`는 display:none만 빼고 font-size:0 조각은 그대로 남긴다(직접 확인). 그래서 innerText로는 부족하다.
- **reordering**: Bad Characters(IEEE S&P 2022)는 지각할 수 없는 공격을 4종으로 나눈다. 보이지 않는 문자, 닮은꼴 문자, 재정렬(RLO U+202E, LRO U+202D, PDF U+202C, LRI U+2066, PDI U+2069), 삭제(백스페이스 U+0008)다. 방어책으로는 "보이지 않는 문자 제거", "Bidi 알고리즘을 적용해 제어 문자를 해소", "삭제 문자를 미리 해소"를 제안했다. 렌더링 후 OCR은 "보이지 않는 문자, 재정렬, 삭제 공격을 100% 막는다"고 했다. CSS `unicode-bidi:bidi-override`와 flex `order`도 같은 재정렬 효과를 낸다(직접 확인).

**시사점 (추가)**: 블록 요소마다 "보이는 글자열"을 하나 더 만들어 키워드 매칭에 쓴다.
1. 숨김 판정(§2·§3)에서 숨김으로 나온 자손 텍스트는 뺀다(salting 대응).
2. 계산된 `unicode-bidi`가 `bidi-override`이고 `direction:rtl`이면 글자열을 뒤집는다. 문자열 안의 U+202E…U+202C 구간도 뒤집은 뒤 제어 문자를 지운다. U+0008은 앞 글자와 함께 지운다.
3. flex·grid 컨테이너는 자식을 화면 좌표(rect.left, top) 순으로 정렬해서 잇는다.
4. `::before`·`::after`의 content는 `getComputedStyle(el, '::before').content`로 읽어 앞뒤에 붙인다(02 §1에 항목만 있음. 구현 위치를 명시).

- 기법 코드: salting에서 **숨긴 조각**이 걸리는 기법(OFFSCREEN 또는 TRANSPARENT)은 04 규칙 그대로다. 보이는 쪽이 광고인 경우는 4종이 아니므로 `result_extra.json`(ETC "SALTED_TEXT")으로 보낸다. bidi·order 재정렬도 4종이 아니므로 ETC "REORDERED_TEXT"로 보낸다. 다만 재정렬된 글자가 숨김이나 변형 신호와 같이 있으면 키워드 매칭이 되어야 하므로, **매칭 단계에는 반드시 넣는다.**

**난이도**: 중간 (1일). 1번과 4번이 핵심이고, 2번과 3번은 각각 몇 줄이다.

## 6. CDP `DOMSnapshot.captureSnapshot`: 한 번 호출로 렌더링 정보 수집 (직접 확인)

**발견**: Chrome DevTools Protocol의 `DOMSnapshot.captureSnapshot`은 다음 옵션과 필드를 제공한다(프로토콜 정의 파일에서 확인).
- `computedStyles`(필요한 속성만 지정), `includePaintOrder`, `includeDOMRects`(offset·client·scroll rect)
- **실험 기능**: `includeBlendedBackgroundColors`("겹치는 모든 요소의 배경색을 합성한 색"), `includeTextColorOpacities`(계산된 글자 불투명도)
- `textBoxes`: 실제로 배치된 글자 조각과 그 좌표
- 설명문에 따르면 **Shadow DOM은 평탄화**되어 나온다. iframe은 `documents` 배열에 별도 문서로 나온다.

직접 확인 결과:

| 확인 항목 | 결과 |
|---|---|
| 속도 | 행안부 메인(노드 5,455개, iframe 포함 문서 2개) **49ms**, 정부24 메인(노드 3,192개) **42ms**. 1920×1080, M 시리즈 Mac |
| display:none | layout 배열에서 빠진다 → 렌더링 여부를 바로 알 수 있다 |
| 형제 absolute 검은 상자 위 검은 글자(04에서 elementsFromPoint가 필요했던 경우) | blendedBackgroundColor = `rgb(0,0,0)` → 바로 대비 1.0 |
| 부모 opacity:0 | 요소의 textColorOpacity = 0 |
| 어두운 배경 위 흰 글자 | 배경 `rgb(18,52,86)` → 보임 (정답) |
| `::before` content | `::before` 노드로 글자가 나온다 |
| zoom:0.01, scale(0.02) | 텍스트 bounds 높이 0~0.4 → OFFSCREEN 신호 |
| **한계 1: mix-blend-mode:difference인 흰 글자** | 배경을 흰색으로 줘서 **"안 보임"으로 오판**한다(실제로는 검게 보임) |
| **한계 2: 그라데이션 배경** | 단색 그라데이션은 그 색으로 근사해서 준다. 여러 색 그라데이션의 처리 방식은 확인하지 못했다 → 04처럼 background-image가 있으면 차분으로 보낸다 |

**시사점 (선택적 변경)**: 판정 JS를 요소마다 돌리지 않고, **1차 후보 추출을 DOMSnapshot 한 번으로** 할 수 있다. 렌더링 여부, 글자 박스, 합성 배경색, 누적 불투명도, 페인트 순서를 한 번에 얻는다. 그 뒤 광고성을 통과한 후보만 JS로 정밀 판정하고 차분한다. 이 방식이 시간 점수(20점)와 정확도에 모두 유리하다.
- 위험: `blendedBackgroundColors`와 `textColorOpacities`는 experimental 필드다. Chromium 버전을 고정해서 동봉하므로 실행 중에 바뀔 위험은 낮다. 다만 **이 값만으로 최종 판정하지 말고**, mix-blend-mode·filter·background-image가 있으면 차분으로 보낸다.
- 04의 JS 방식이 이미 48개 케이스로 검증되어 있으므로 **9일 일정이면 "보조 신호 + 속도 최적화"로만 쓰는 것을 권장한다.** 04 판정 결과와 다른 경우를 로그로 남겨 비교한다.

**난이도**: 중간 (1~2일). Playwright Python에서 `context.new_cdp_session(page)`로 바로 호출된다(직접 확인).

**출처**: ChromeDevTools/devtools-protocol `pdl/domains/DOMSnapshot.pdl` — https://github.com/ChromeDevTools/devtools-protocol/blob/master/pdl/domains/DOMSnapshot.pdl (문서 사이트 https://chromedevtools.github.io/devtools-protocol/tot/DOMSnapshot/ 는 이번에 리다이렉트 안내만 받았다)

## 7. 한국어 정규화 보강

### 7.1 `ㆍ`(U+318D 아래아)는 구분자로 처리 (코드로 확인)
- `ㆍ`는 호환 자모 블록(U+3131–318E) 안에 있다. 그런데 공문서에서는 가운뎃점으로 아주 많이 쓴다(`시ㆍ도`). 04 §6.2 SEP 목록에는 `·`(U+00B7)와 `•`만 있고 `ㆍ`, `‧`(U+2027), `・`(U+30FB), `･`(U+FF65), `∙`(U+2219), `⋅`(U+22C5)는 없다. 그래서 `카ㆍ지ㆍ노`는 SEP로 지워지지 않아 매칭되지 않는다.
- **변경**: 위 6개 글자를 SEP에 넣는다. 그리고 `ㆍ`는 "자모 글자 있음 → JAMO" 판정에서 뺀다. 그러지 않으면 정상 공문의 `ㆍ`가 JAMO 근거 글자로 잡힌다.

### 7.2 여러 글자로 자모 하나를 만드는 변형 (korcen)
- korcen(Tanat05/korcen, **MIT**, 2026-05-27 갱신)의 한국어 비속어 필터 정규화 표를 소스에서 직접 확인했다.
  - 다중 글자: `77→ㄲ`, `刀卜→까`, `ㅇㅣ-ㅣ→애`, `lㅣ→니`, `ㅇl=스→섹스`, `_ㅣ_→ㅗ`, `／＼→ㅅ`
  - 단일 글자: `┻ ┴ ⊥ † ╨ → ㅗ`, `甘 廿 田 口 日 目 囗 → ㅂ`, `己 乙 已 巳 → ㄹ`, `匚 → ㄷ`, `卜 r F 丨 | / → ㅏ`, `H Н ℍ → ㅐ`, `人 ^ ∧ Λ → ㅅ`, `0 O o ○ ◎ → ㅇ`, `朝 兆 早 鳥 → 조`
  - 구조: 오탐 패턴(정상 단어)을 먼저 지운 다음 매칭한다(`FALSE_POSITIVE_PATTERNS_*`). 정규화 표를 거꾸로 뒤집어 원문 위치를 찾는 정규식(`build_flexible_regex`, 글자 사이 `\s*` 허용)을 만든다.
- **시사점 (추가)**: KOTOX·스팸체 표에 없는 글자(박스 그림 문자 ┻, 甘 田 目, 已 巳, 匚, Н)와 **다중 글자 규칙**을 한국어 닮은꼴 표에 합친다. `ㅇㅣ-ㅣ`(애)처럼 "가로 쪼개기 + 기호"가 섞인 형태는 04 §6.3에 없다. "정상 단어 먼저 제거" 구조는 §7 광고성 판정의 미끼 처리(`토토로`, `주차 슬롯` 등)에 그대로 쓸 수 있다.
- 주의: korcen 표는 욕설용이라 `ㅣ→ㅏ`, `1→ㅣ`처럼 공격적이다. **키워드 일치가 있을 때만** 적용한다(04 §5.4 C와 같은 조건).

### 7.3 결합 부호 제거 (코드로 확인)
- `cásínó`, `카̈지노`(U+0308 결합)는 skeleton·NFKC로 풀리지 않는다. `NFD → 범주 Mn 제거 → NFC`를 하면 `casino`, `카지노`가 된다(한글 음절은 NFD로 첫가끝 자모(Lo)가 되므로 Mn 제거에 영향을 받지 않는다).
- **변경**: 04 §5.4에 규칙 E "결합 부호 제거 후 키워드 일치"를 추가한다. 기법 코드는 HOMOGLYPH다(겉모양이 같은 다른 코드). 키워드 일치를 요구한다.

**난이도**: 7.1~7.3 합쳐 반나절.

**출처**: Tanat05/korcen `korcen/korcen.py` — https://github.com/Tanat05/korcen (GitHub API로 라이선스·소스 확인)

## 8. SVG 글자와 입력 필드 (직접 확인)

- **SVG `<text>`**: `fill="#fff"`인 흰 글자의 계산된 `color`는 `rgb(0,0,0)`이고 `fill`만 `rgb(255,255,255)`다. `fill-opacity="0"`도 color에는 나타나지 않는다. 04 §3.1은 color와 text-fill만 보므로 **SVG 투명 글자를 놓친다.** → SVG 안의 텍스트는 `fill`, `fill-opacity`, `stroke`, `stroke-opacity`로 판정한다.
- **`<input value="…">`, `placeholder`, `<textarea>`**: input의 value는 텍스트 노드가 아니다. TreeWalker로 텍스트 노드를 모으면 빠진다(직접 확인). 흰 배경 + 흰 글자 input은 TRANSPARENT 후보가 될 수 있다. → `input[value]`, `[placeholder]`, `textarea`, `option`의 텍스트도 후보로 넣는다. location은 그 요소다.
- 출제 가능성은 낮다. 다만 비용이 작아서 넣는 편이 낫다.

**난이도**: 낮음.

## 9. 숨김 링크 블록의 특징 (광고성 점수 보조)

| 특징 | 근거 | 확인 수준 |
|---|---|---|
| 숨김 상자 하나에 외부 링크가 여러 개 몰림(예시마다 15~23개), 페이지 끝(`</body>` 직전)에 위치 | Securelist 2025-10-17 예시 1~4 | 원문 확인 |
| `rel="dofollow"`(HTML 표준값이 아님) — "숨김 블록 + dofollow 외부 링크는 SEO 스팸 주입을 명확히 가리킨다". 단 예시 3·4에는 없었다 | Securelist | 원문 확인 |
| 앵커 텍스트의 언어·주제가 페이지와 섞임("mixed languages and topics in the anchor text") | Netcraft, "How fraudsters are poisoning search results to promote phishing sites" (2025-06-17) | 원문 확인. 터키 도박 SEO 업자(Neon SEO Academy, 15,000개 이상 도메인 주장) |
| 터키어 `deneme bonusu`(체험 보너스) 앵커 | 검색 요약에만 나옴 | **확인 못 함** (원문에서 찾지 못했다) |
| 주입 태그 수가 적음(26%가 1개, 70%가 10개 미만) | DMoS | 원문 확인 |

**시사점 (추가)**: 광고성 점수에 키워드 외 신호를 더한다. ① 숨김 후보 안의 `<a href>`가 **외부 도메인**이다. ② 그런 링크가 한 상자에 3개 이상 있다. ③ `rel`에 `dofollow`가 있다. ④ 앵커 텍스트가 한글 페이지에서 비한글(라틴·터키어·인도네시아어) 도박어다. 키워드 사전에 없는 외국어 광고도 이 신호로 잡을 수 있다. 다만 **이 신호만으로 출력하지는 않는다**(정상 숨김 메뉴에도 외부 링크는 있다). 키워드 점수가 애매할 때 가산점으로만 쓴다.

**난이도**: 낮음.

**참고 수치(논문)**: DMoS 운영 결과 재현율 99% 이상, 정밀도 약 89%(5개월 시범 운영, 웹 페이지 3,800만 개). 은어 정규화(JNA: 병음 편집거리 + 한자 모양 해시 Four-Corner)를 넣으면 정밀도가 91.29% → 94.89%로 오른다. JNA 자체는 정상 페이지 40,426개 중 4개 페이지에서 7건만 잘못 잡았다(그중 2건은 원문 오타). 우리 HOMOGLYPH 보충표를 "모양 해시"로 자동 확장하는 아이디어의 근거로 쓸 수 있다(§10.3).

## 10. 그 밖의 확인 결과

### 10.1 불필요로 판단한 것
| 항목 | 확인 결과 | 판단 |
|---|---|---|
| 접근성 트리 비교(CDP `Accessibility.getFullAXTree`)로 숨김 판정 | sr-only, opacity:0 부모 안의 글자, 흰 배경의 흰 글자가 **모두 ignored=false**였다. display:none만 트리에서 빠진다(직접 확인) | **불필요**. 시각적 숨김을 구분하지 못한다 |
| OCR로 최종 확인(PhantomLint 방식) | PhantomLint(arXiv 2508.17884, 2025)는 Playwright로 렌더링한 뒤 블록을 잘라 Tesseract로 OCR하고, 추출 글자와 비교해 "보이지 않는 글자"를 찾는다. **의심 문구 필터를 먼저 거친 블록만** OCR한다(우리 "광고성 통과 후보만 차분"과 같은 구조). 오탐률 0.092%(ICML 논문 3,257편 중 3편). 단 **문서당 43~68초**(M1 Pro). 낮은 대비 영역은 가우시안 블러를 먼저 적용해 `#fefefe/#fff` 글자를 OCR이 읽지 못하게 한다 | **불필요**(본 경로). 우리 픽셀 차분이 더 싸고 같은 역할을 한다. 기획서에 "PhantomLint와 같은 '의심 후보만 렌더링 검증' 구조"라고 근거로 인용할 수 있다 |
| `checkVisibility({contentVisibilityAuto:true})` | 화면 아래 `content-visibility:auto` 구역의 **정상 텍스트도 false**가 나온다. 기본 옵션은 true(직접 확인) | **쓰지 말 것**. 쓰면 오탐이 생긴다 |

### 10.2 04 규칙으로 이미 잡히지만 명시할 것
- **CSS `zoom:0.01`**: 계산된 `font-size`는 **16px 그대로**다(직접 확인). font-size ≤ 1px 규칙으로는 못 잡고, 04 §2.1 3)의 글자 박스 붕괴(높이 0)로 잡힌다. 기법 코드 표(04 §4.1)의 OFFSCREEN 행에 `zoom`을 추가한다.
- **`clip-path: circle(0)`, `polygon(0 0,0 0,0 0)`**: 04는 `inset()`만 계산한다. Talos의 "반지름 0인 원" 사례가 이것으로 보인다. 직접 확인 결과 `elementFromPoint(글자 위치)`가 해당 요소를 반환하지 않았다. → clip-path가 none이 아니고 inset이 아니면 `elementFromPoint`로 확인한다. 단 `pointer-events:none`인 요소는 원래 elementFromPoint에 걸리지 않는다. 그러니 clip-path가 있을 때만 이 검사를 쓴다.
- **`filter: blur(20px)`**: 글자를 읽을 수 없지만 4종 정의에 없다 → ETC 후보.

### 10.3 선택 (시간이 남으면)
- **글리프 이미지로 닮은꼴 표 자동 생성(ShamFinder 방식)**: ShamFinder(IMC 2019)는 GNU Unifont 글리프를 32×32 비트맵으로 그리고, 다른 픽셀이 4개 이하(Δ≤4)인 글자 쌍을 닮은꼴로 본다. 그 결과 SimChar 13,208쌍을 만들었는데, UTS #39 confusables와 겹치는 것은 **127쌍뿐**이었다. 블록별로는 한글 음절 8,787자가 가장 많았다. → Windows 기본 글꼴(맑은 고딕)로 한글 자모와 한자·가나·기호를 렌더링해 비교하면, KOTOX·스팸체 표에 없는 후보를 **오프라인으로** 뽑을 수 있다. 결과는 사람이 검수한 뒤 표에 넣는다. 반나절~1일. 오탐 위험 때문에 키워드 일치 조건을 유지한다. 출처: Suzuki et al., "ShamFinder: An Automated Framework for Detecting IDN Homographs", IMC 2019 — https://arxiv.org/abs/1909.07539 (본문 https://ar5iv.labs.arxiv.org/html/1909.07539)

### 10.4 한계로 기록할 것 (기획서 "한계" 절)
- **웹폰트 치환 암호**: Proofpoint(2019-01-03)가 보고한 피싱 키트는 CSS `@font-face`에 base64로 넣은 WOFF/WOFF2 글꼴로 글자 모양을 바꿔 그렸다. 그래서 소스의 뒤섞인 글자가 화면에서는 정상 문장으로 보인다. 같은 수법을 광고에 쓰면 DOM 텍스트 기반 탐지는 놓친다. 이 경우는 OCR로만 잡힌다. 또 우리가 글꼴 요청을 차단해도 **data: URL 글꼴은 차단되지 않는다.** 출처: https://www.proofpoint.com/us/threat-insight/post/phishing-template-uses-fake-fonts-decode-content-and-evade-detection
- **mix-blend-mode·filter로 색을 바꾼 글자**: 계산값으로는 판정할 수 없다. 차분으로만 판정한다(§3, §6).
