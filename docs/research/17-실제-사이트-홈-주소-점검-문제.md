## 문제 1. 사이트 안 어디에도 링크가 없는 광고 (고칠 수 없음, 표 분류 변경)

## 문제 2. 머리말·꼬리말 버튼을 쪽마다 다시 누른다 (느림, 원인 확인)

- 측정
  - bd.kma.go.kr: 90초에 12쪽. `clicks` 평균 46초. 클릭 208번, 다시 열기 87번(1번에 평균 1.5초)
  - chunggong.or.kr: 60초에 19쪽. `clicks` 평균 23.5초. 누를 때마다 "로그인 유지" 경고창이 뜬다
- 원인
  - 클릭 템플릿 키가 `(페이지 패턴, 프레임 패턴, 함수명)`이다
  - 그래서 모든 페이지에 똑같이 있는 함수를 새 페이지 패턴마다 다시 누른다
    - 예: `fn_facebookGo`, `fn_twitterGo`, `goLoginPage`, `loginAction`, `fn_fuSionViewGo`, `extendSession`, `sessionPop_Close`
  - 누를 때마다 페이지를 다시 연다 (`reopen` = 이동 + load 대기 + 안정화)
  - bd.kma.go.kr 기준으로 페이지당 후보는 약 17개다. 1분에 12개 패턴이면 같은 꼬리말 함수를 12번 누른다
- `@ev:` 묶음(리스너만 있는 요소)은 이미 `ev_miss`로 걸러진다: 다른 페이지 2곳에서 얻은 게 없으면 그만 누른다. 이름 있는 함수에는 이 장치가 없다
- 함정: "인자 없는 함수는 어디서 눌러도 같다"고 보면 안 된다
  - `moveList()`는 인자가 없지만 페이지 안 숨은 폼(`detailForm`)의 게시판 값을 읽어 게시판마다 다른 목록으로 간다
  - 이름만으로 묶으면 다른 게시판 목록을 잃는다
- 제안
  - 함수명별로 "서로 다른 페이지 패턴 2곳에서 눌렀더니 얻은 요청이 같았다(또는 둘 다 없었다)"면 사이트 공통 버튼으로 표시한다
  - 표시된 함수는 이후 모든 페이지에서 누르지 않는다 (`ev_miss`와 같은 방식)
  - `moveList()`처럼 페이지마다 결과가 다른 함수는 두 결과가 달라서 계속 누른다
- 기대 효과
  - bd.kma.go.kr은 첫 2개 패턴 뒤로 꼬리말 함수 약 10개를 건너뛴다
  - 쪽당 시간이 절반 이하로 줄 것으로 보인다 (구현 뒤 측정 필요)

## 문제 3. GET 수정·삭제 주소를 방문한다 (안전, 우선 수정 필요)

- edugrad.silla.ac.kr에서 4분 동안 `mode=del&idx=N` 33쪽, `mode=edit&idx=N` 34쪽을 열었다. 방문한 198쪽의 34%다
- 이번에는 비밀번호 확인 화면이라 글은 지워지지 않았다
  - 확인: `mode=view&idx=436`이 이후에도 그대로 열리고, 삭제·수정 화면에는 비밀번호 칸이 있다
- 원인: `DANGER`는 `delete`·`remove`·`write`·`modify`·`update` 같은 단어만 본다
  - 쿼리 값의 줄임말 `mode=del`, `mode=edit`, `act=del`, `cmd=del`은 거르지 못한다
- 같은 계열이 클릭 후보에도 있었다 (bd.kma.go.kr)
  - `fileDel()`: 입력칸만 비움, 무해
  - `doReg3()`: 빈 칸이면 경고만 띄움, 무해
  - 다만 `fn_del(123)`처럼 인자가 있는 삭제 함수는 지금 규칙을 통과한다
- 제안
  - 쿼리 값이 동작 이름이면 위험 주소로 본다: `[?&](mode|act|cmd|action|proc|job|w|type)=(del|delete|edit|modify|update|write|reply|regist|reg)(&|$)`
  - 클릭 후보는 함수명이 `del`·`edit`·`reg`로 끝나거나 그 단어를 포함하면(`fnDel`, `goEdit`, `doReg`) 누르지 않는다
  - 둘 다 `ctx.route`에도 쓰는 JS 호환 정규식이어야 한다 (DANGER 주석 참고)
- 효과: 위험을 막고, silla.ac.kr에서는 크롤 예산의 34%가 실제 글로 간다

## 문제 4. 서버 한 대가 자기 자신으로 301을 보내 무한 이동 (서버 오류, 재시도로 우회)

- bd.kma.go.kr 루트 `/`를 curl로 6번 요청: 5번은 `http://bd.kma.go.kr/`(정상), 1번은 `https://bd.kma.go.kr/`(자기 자신)
- 브라우저는 keep-alive로 같은 서버에 다시 붙어 `ERR_TOO_MANY_REDIRECTS`로 끝난다
- 측정: 새 컨텍스트 10번 중 6번 무한 이동, 같은 컨텍스트 6번은 모두 성공
- 처음에는 Chromium HTTPS 자동 업그레이드 탓으로 봤으나 끄고도 같아서 되돌렸다
- 지금은 `NOT_SERVER`가 `ERR_TOO_MANY_REDIRECTS`를 "서버 문제 아님"으로 보고 재시도하지 않는다
- 제안
  - **시작 주소만** 무한 이동이면 새 컨텍스트(새 연결)로 2번까지 다시 연다
  - 1번 성공 확률이 약 40~50%라 3번이면 80~88%다
  - 시작 주소 밖의 주소는 지금처럼 재시도하지 않는다

## 문제 5. HTTP 429(요청 과다)를 받으면 바로 끝난다

- ysgsa.yonsei.ac.kr은 같은 날 크롤을 여러 번 돌린 뒤 일반 브라우저 UA에도 429를 준다
- 프로그램은 시작 주소가 400 이상이면 "열지 못함"으로 0.5초 만에 끝난다
- 실제 점검에서는 한 번만 돌리니 흔하지 않다. 다만 크롤 도중 429를 받으면 그 뒤 페이지를 모두 잃는다
- 제안
  - 429·503이면 `Retry-After`만큼(없으면 30초, 최대 60초) 기다린다
  - 동시 접속을 반으로 줄인다 (`fail()`과 같은 경로)
  - 같은 주소를 1번 다시 넣는다
  - 시작 주소가 429면 기다렸다가 1번 더 연다

## 문제 6. 오탐 의심: 공지·사진 게시판의 ATTR_META_AD (확인 필요)

- ari.snu.ac.kr 공지(`mid=notice&document_srl=75311·54455`)와 edugrad.silla.ac.kr 사진(`pCode=photo&idx=3076·3014`)에서 `ATTR_META_AD`(제목·메타·속성 속 광고)가 나왔다
- 공지·사진 게시판은 스팸이 드문 곳이라 오탐일 수 있다. 어떤 속성 값 때문인지 결과 파일에서 확인해야 한다
  - 둘 다 `result_extra.json`에만 나오고 채점용 필수 4종에는 영향이 없다
